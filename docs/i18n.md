# Languages (i18n)

> **Status: implemented and tested (2026-10-28).** English, Spanish and Portuguese, exposed as `@danielsoaresf/lost-ui/i18n` and from the root entry. Related: [forms.md](forms.md), [stack.md](stack.md).

## 1. What it covers

The texts the components bring: the `FormBuilder` buttons, the placeholders and button names of the fields ("Pick a date", "Clear date", "Increment"…), the "No results" of the lists, the screen-reader texts of the `ui` primitives ("Close", "Previous slide", "Toggle Sidebar"…) and the **default messages of the validation rules** ([forms.md](forms.md) section 5).

It does not cover what an app writes (labels, its own messages), the names of countries (they come from `Intl.DisplayNames` in the field's `locale`) and the month and weekday names of the calendar (they follow the `locale` prop of `FormInputDate`).

## 2. Using it

```tsx
import { LostI18nProvider } from "@danielsoaresf/lost-ui/i18n";

<LostI18nProvider language={language}>
  <App />
</LostI18nProvider>;
```

`language` is `"en"`, `"es"` or `"pt"`; a regional code such as `"pt-BR"` uses the texts of its language and any other language falls back to English. Without the provider everything is in English. The provider only sets the language of the library, so an app that has its own i18next passes it the language it already tracks: `language={i18n.language}`.

A text given by prop always wins over the translation (`<FormInputDate placeholder="Pick one" />`, `<FormBuilder submitLabel="Save" />`).

`pt` is Brazilian Portuguese.

## 3. How it is built

- `lost-ui` creates **its own** `i18next` instance (`lostI18n`) with the three languages inline in the bundle, so it never touches the instance of the app and needs no loading step. `i18next` and `react-i18next` are regular dependencies of the package.
- Components read it with `useLostTranslation()`, which also renders them again when the language changes. Code outside React (the rules) uses `translate(key, options)`.
- The texts live in `src/i18n/locales/{en,es,pt}.ts`. `en.ts` defines the shape; the other two are typed against it, so a missing key does not compile, and a test checks that every language has the same keys and placeholders.

## 4. The app's own texts

An app can put its texts in the same instance, so one language switch changes the app and the library:

```tsx
import { registerMessages, useLostTranslation } from "@danielsoaresf/lost-ui/i18n";

registerMessages("app", {
  en: { welcome: "Welcome, {{name}}" },
  pt: { welcome: "Bem-vindo, {{name}}" },
});

const { t } = useLostTranslation("app");
t("welcome", { name: "Ada" });
```

An app that already runs its own i18next can keep it and only set `LostI18nProvider` to the same language.

## 5. Adding a language

1. Create `src/i18n/locales/<code>.ts` typed as `Messages`.
2. Add the code to `lostLanguages` and the file to `lostMessages` and `resources` in `src/i18n/i18n.ts`, and to the toolbar in `.storybook/preview.ts`.
3. The key and placeholder test in `src/i18n/i18n.test.tsx` covers it as soon as it is in `lostLanguages`.

## 6. Storybook

The toolbar has a **Language** switch (English, Español, Português). It wraps every story in `LostI18nProvider`, so a story shows the texts of the language chosen.

## 7. Known gaps

- The `nav` landmark names `"breadcrumb"` and `"pagination"` are still fixed English.
- `emoji-picker-react` and `react-day-picker` bring their own texts; only the search placeholder of the emoji picker is translated.
- The `FormInputDate` calendar does not take a locale for its internal labels yet.
